# Ground missing project context

Read the current entry documents and registered sources first. A repair should not restart an intake interview when the needed facts are already available.

Find enough evidence to explain the project's purpose, scope, current goal, responsible sources, and operating boundaries. Ask only for an unknown that changes the authorized action or its conclusion. Use ordinary project language, not governance terminology.

For a new project with little context, invite a short answer or existing sources:

```text
What is the project for, and what outcome matters next?
Which existing documents, repositories, or trackers should I use?
Are there access or working boundaries I need to preserve?
```

Adapt this to what is already known. Do not require a formal lifecycle label, comprehensive source inventory, or all future feature decisions before useful work can begin. Stop asking when remaining unknowns do not affect the current task.

Classify supplied sources by what they actually own. A task checklist may explain one release without defining the whole project. A public website describes public claims or observed behavior; it is not automatically the internal project authority.

Reflect proposed ownership briefly before changing it. Ask for a decision only if competing interpretations materially change authority or scope. An existing coherent convention can be adopted within an authorized repair without another approval round.

For unavailable external sources, record the access limitation and continue independent work. Ask for the required access or facts only if they are necessary to finish the task. Do not copy an old export into the canonical role.

For stale work lists, establish current priorities before reviving old pending items. Combine questions that resolve the same outcome across several documents. Respect skipped items; retain their uncertainty only where relevant.

If the user wants the kernel before all facts are known, create usable routes and explicitly scoped unknowns. Report `READY_WITH_GAPS`, naming the actual missing facts and the work that can continue. Do not label optional formatting or a missing machine marker as a project gap.
